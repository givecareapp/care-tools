# Code Review: care-tools (2026-01-28)

## Scope

This is a **documentation-only** repository containing the GC-SDOH-30 assessment framework and supporting tooling (agent workflow scaffolding, specs, state tracking). No runtime code exists. The review covers framework correctness, documentation coherence, infrastructure health, and issues **not already captured** by the 17 pending specs.

---

## Code Quality

### Already-specced issues (skipping)

Specs 001-017 cover the major framework bugs (Q29 reverse-scoring, scale mismatch, zone ordering, placeholders, missing CONTRIBUTING.md, etc.). These are not repeated here.

### NEW: P6 "Emotional Wellbeing" zone is mislabeled
`GC-SDOH.md:198-210` — The P6 zone is labeled "Emotional Wellbeing" but its two questions are:
- Q27: "I feel prepared for caregiving emergencies" (emergency preparedness)
- Q28: "I feel safe in my neighborhood" (physical safety)

Neither question measures emotional wellbeing (depression, anxiety, burnout). The zone resources at line 210 list "mental health services" but the questions don't screen for mental health. This is a content-validity issue: the zone label promises something the questions don't deliver. Compare to P1 Q4 ("I can talk to others about my caregiving challenges") which is closer to emotional wellbeing than anything in P6.

**Recommendation:** Rename the zone to "Safety & Preparedness" or add actual emotional wellbeing questions (PHQ-2 derivative, burnout screening).

### NEW: Q30 scoring direction is undocumented
`GC-SDOH.md:222-224` — Q30 ("How would you rate your sleep quality?") uses Very Poor=1 to Excellent=5. This means higher scores = better outcomes, matching the non-reverse-scored pattern. But Q29 (exhaustion, higher = worse) is in the same P2 zone. After spec 013 adds Q29 to the reverse-scored list, P2 will have one reverse-scored and one non-reverse-scored question. This asymmetry should be explicitly documented to prevent implementer confusion.

### NEW: Ledger stats are inconsistent
`state/ledger.json:10` — `totalReviewFindings: 85` but `findings-2026-01-27.json` contains exactly 17 findings, and there is only one findings file. Either the ledger is counting something different from what it claims, or earlier findings were discarded without decrementing the counter. Similarly, `totalFindingsActioned: 0` despite all 17 findings having `"status": "actioned"` in the JSON.

### NEW: Spec completion signal references nonexistent tooling
`constitution.md:16-17` specifies `npm run build` and `npm run test` as completion signals. There is no `package.json`, no Node.js project, and no test suite. Every spec inherits these signals via the agent workflow, meaning the Ralph agent will never successfully mark a spec as complete — even for pure documentation fixes.

## Architecture

### NEW: Findings file doesn't match ledger schema
`state/ledger.json` has `"specs": {}` (empty object) and `"findings": []` (empty array), while `state/findings-2026-01-27.json` has the actual 17 findings. The ledger appears disconnected from the findings — it doesn't reference or aggregate them. If the ledger is supposed to be the source of truth, its data is stale.

### NEW: Spec-finding duplication
Specs 001-005 and 013-015 cover overlapping issues. For example:
- Spec 002 (scoring contradiction for reverse items) and spec 013 (fix Q29 reverse-scoring omission) address the same root cause
- Spec 004 (Q29 scoring direction is ambiguous) is the diagnostic finding; spec 013 is the fix

This isn't necessarily wrong, but it means completing spec 013 should also close specs 002 and 004. There's no linkage mechanism between specs to prevent duplicate work.

### NEW: No `.gitignore` rules for operational state
The `.gitignore` at the repo root doesn't appear to exclude `state/`, `logs/`, or `reports/`. These are ephemeral operational artifacts (nightly agent output) that will accumulate unbounded in the git history. Date-stamped files like `findings-2026-01-27.json` and `ai-review-2026-01-27.md` will grow linearly with each nightly run.

## Testing

### NEW: No way to validate scoring claims
The document states specific risk thresholds (Low >= 3.5, Moderate 2.5-3.49, High < 2.5) but provides no test vectors. Minimum viable validation would be three reference profiles:

1. **All-positive caregiver**: answers 5 on all non-reverse, 1 on all reverse items. Expected: all zones Low Risk.
2. **All-negative caregiver**: answers 1 on all non-reverse, 5 on all reverse items. Expected: all zones High Risk.
3. **Mixed-risk caregiver**: P4 high-risk, others moderate. Expected: Overall Moderate Risk.

This is covered by spec 014 but bears repeating since it blocks any implementation work.

### NEW: Adaptive pattern threshold has no sensitivity analysis
`docs/ADAPTIVE-ASSESSMENT-PATTERN.md:155-156` claims the Quick-6 should have "sensitivity >85%" and "false-negative rate <10%" but provides no baseline data, pilot plan, or method for measuring these. These targets are aspirational without a validation protocol.
